# Self A2A Failure Modes

이 문서는 하나의 AI 하네스가 역할을 나누어 수행할 때 생기는 고유한 실패 모드를 줄이기 위한 공통 기준이다.

## 목적

Self A2A는 역할 분리처럼 보이지만 실제 실행 주체가 같기 때문에 검토가 약해지거나, 오래된 전제가 반복되거나, 이전 판단을 스스로 정당화하는 문제가 생길 수 있다.

따라서 긴 작업, normal 이상 작업, 컨텍스트 재개 작업, reviewer/tester가 필요한 작업에서는 이 문서를 함께 확인한다.

## 주요 실패 모드

### Role Drift

역할이 섞여 Worker가 Reviewer 결론까지 대신 내리거나, Reviewer가 새 기능을 제안하고 구현 방향을 끌고 가는 현상이다.

대책:

- 각 단계 시작 전에 현재 역할과 금지 사항을 짧게 재확인한다.
- Reviewer는 구현하지 않고 문제 탐지만 한다.
- Tester는 검증 결과를 추정하지 않고 실행 여부와 결과를 분리해서 적는다.

### Consensus Rot

Planner, Worker, Reviewer가 서로 다른 관점처럼 보이지만 실제로는 앞 단계 결론을 그대로 반복하며 검토 강도가 떨어지는 현상이다.

대책:

- Reviewer는 최소 한 번 "이 변경이 틀렸다면 어디서 틀릴 수 있는가"를 확인한다.
- 리뷰 결과에는 근거 파일, 실행 결과, 관찰된 UI 중 하나 이상을 포함한다.
- 근거가 없으면 "확인하지 못함"으로 남기고 통과로 간주하지 않는다.

### Context Rot

오래된 대화, 이전 구현 의도, 이미 바뀐 파일 상태를 현재 사실처럼 취급하는 현상이다.

대책:

- 작업 재개, 긴 작업, 파일 변경 후에는 관련 파일을 다시 읽는다.
- 사용자 발언보다 현재 파일 상태가 우선 필요한 경우 실제 파일을 기준으로 판단한다.
- 이전 결론을 사용할 때는 현재 코드와 충돌하지 않는지 확인한다.

### Rubber-Stamp Review

자기 구현을 스스로 리뷰하면서 "문제 없어 보임"으로 지나가는 현상이다.

대책:

- Reviewer는 칭찬이나 요약보다 결함 탐색을 우선한다.
- 문제가 없을 때도 남은 테스트 공백이나 확인하지 못한 영역을 적는다.
- UI 작업은 코드만 보고 통과시키지 않고 가능한 경우 화면 결과를 확인한다.

### Scope Creep Normalization

작업이 커졌는데도 처음 위험도 그대로 진행하는 현상이다.

대책:

- 수정 파일 수, 공통 실행 계층 영향, 저장/삭제, 공통 UI 영향이 늘어나면 즉시 escalation 한다.
- 위험도가 올라가면 필요한 특화 역할을 추가한다.
- 원래 요청과 직접 관련 없는 리팩토링은 분리한다.

### Validation Theater

검증을 한 것처럼 보이지만 실제로는 빌드 통과만으로 UX, 데이터, 런타임 동작까지 통과했다고 간주하는 현상이다.

대책:

- 타입체크, 빌드, 브라우저 확인, API 확인, 데이터 보존 확인을 서로 다른 검증으로 구분한다.
- 실행하지 않은 검증은 이유와 잔여 리스크를 남긴다.
- "빌드 통과"는 화면 정상 동작의 증거로 쓰지 않는다.
- "적용됨", "해결됨", "검증 완료"는 실제 관찰 근거가 있을 때만 사용한다.
- DOM 상태로만 확인한 경우 화면 UX 검증과 구분해서 적는다.

### Autopilot Drift

사용자가 컨펌 없이 계속 진행하라고 했을 때, 단계 경계가 흐려지고 미검증 항목을 다음 단계에서 사실처럼 취급하는 현상이다.

대책:

- 단계 종료마다 완료한 것, 검증한 것, 남은 리스크, 다음 단계 판단을 짧게 남긴다.
- 컨펌 없는 순차 진행에서는 전체 단계 목록에서 완료/진행 중/남은 단계를 함께 표기한다.
- 보고는 승인 요청이 아니라 작업 경계 기록으로 취급한다.
- 다음 단계는 이전 단계의 미검증 항목을 전제로 삼지 않는다.
- 미검증 항목이 다음 단계의 전제가 되면 먼저 검증하거나 escalation 한다.

### Completion Inflation

작은 단계의 완료를 전체 기능 완료처럼 표현하거나, 정적 검증을 사용자 흐름 검증으로 확장해서 말하는 현상이다.

대책:

- 단계 완료, 기능 완료, UX 완료, 적용 완료를 분리해서 적는다.
- "완료"라는 표현은 검증한 범위에만 사용한다.
- 전체 목표의 남은 단계를 항상 함께 남긴다.
- 검증하지 않은 사용 시나리오는 잔여 리스크로 남긴다.

### Product Intent Drift

긴 구현 중 제품 목표가 조금씩 바뀌어, 사용자가 원한 흐름보다 구현하기 쉬운 구조로 수렴하는 현상이다.

대책:

- 단계 시작 시 사용자 목표를 한 문장으로 다시 적는다.
- UI 문구와 구조가 사용자 행동 기준인지 확인한다.
- 내부 용어와 구현 편의가 화면 흐름을 지배하지 않는지 확인한다.
- 장기 설계 문서가 있는 경우 현재 변경이 그 설계를 막지 않는지 확인한다.

## Rot Checkpoint

다음 상황에서는 짧게 rot checkpoint를 수행한다.

- 작업이 30분 이상 이어짐
- 컨텍스트 요약 또는 재개 후 다시 작업함
- 변경 파일이 처음 예상보다 늘어남
- 같은 문제를 두 번 이상 수정함
- Reviewer 또는 Tester 판단이 근거 없이 낙관적으로 느껴짐
- 사용자 피드백이 "아직 이상하다", "다시 확인해줘", "없어진 것 같다"에 가까움
- 컨펌 없는 순차 진행에서 단계 보고 없이 다음 단계로 넘어가려 함

확인 항목:

- 현재 판단이 실제 파일 상태에 근거하는가
- 이전 결론을 반복하고 있지는 않은가
- 반대 증거를 찾았는가
- 역할별 책임이 섞이지 않았는가
- 검증하지 않은 것을 통과로 말하고 있지는 않은가
- 이전 단계의 남은 리스크를 현재 단계의 완료 조건으로 잘못 취급하고 있지는 않은가
- 작은 단계 완료를 전체 완료로 부풀리고 있지는 않은가
- 구현 편의 때문에 사용자 목표를 좁히고 있지는 않은가

## Rework Stop Rule

같은 사용자 문제를 두 번째 이상 수정할 때는 새 패치를 바로 적용하지 않는다.

먼저 다음 형식으로 짧게 정리한다.

- Reproduction: 사용자가 겪는 행동을 한 문장으로 재현한다.
- Previous Hypothesis: 직전 수정이 가정한 원인을 적는다.
- Contradiction: 사용자 피드백이 그 가정과 어떻게 충돌하는지 적는다.
- New Invariant: 다음 수정이 반드시 지켜야 할 불변조건을 적는다.
- Verification: 그 불변조건을 어떤 명령, DOM 상태, 화면 조작으로 확인할지 적는다.

이 정리를 하지 못하면 다음 수정은 보류한다.

## 결과 기록 형식

필요할 때 다음 항목을 짧게 남긴다.

- Assumptions: 현재 전제
- Evidence: 확인한 파일, 명령, 화면, 데이터
- Failure Search: 일부러 찾아본 실패 가능성
- Decision: 진행, 수정, escalation 중 무엇을 선택했는가
- Residual Risk: 아직 확인하지 못한 부분
