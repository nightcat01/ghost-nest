## UI Visual Verification Gate

UI/UX를 변경한 작업은 실제 화면 검증을 완료 조건으로 삼는다.

- 타입체크, 빌드, API 응답 확인은 UI 검증을 대체하지 않는다.
- 실제 화면 검증은 브라우저, 스크린샷, DOM 측정, 또는 사용자가 제공한 최신 캡처 중 하나 이상으로 수행한다.
- 화면 검증이 실패하거나 도구 문제로 불가능하면 작업을 "완료"로 보고하지 않는다.
- 이 경우 결과는 "코드 수정 및 정적 검증 완료, UX 검증 미완료"로 분리해서 보고한다.
- 같은 UI 문제를 한 번 이상 재수정했다면, 다음 패치 전 반드시 Rework Stop Rule을 적용해 원인, 검증 방법, 실패 가능성을 먼저 적는다.
- 사용자가 캡처로 깨짐을 지적한 경우, 다음 답변은 구체 원인과 재검증 계획을 포함해야 한다.

# Quality Gates

## User Path Completion Gate

A task is not complete unless the latest requested user path has been verified or explicitly reported as unverified.

For UI, settings, mapping, workflow, save/delete, and generated-data work, completion requires:

- the concrete user path used for verification
- whether the expected option or action was discoverable from that path
- whether the final state persisted or applied correctly
- any path that was not verified and why

Static checks, build success, API success, or DOM presence do not replace user path verification when the request is about screen behavior or user flow.

이 문서는 공용 완료 기준이다.

작업 완료는 기능 구현, 화면 사용성, 검증 결과를 분리해서 판단한다.

## 공통 완료 기준

- 대화형 설계/정리 단계에서 사용자의 실행 지시 없이 소스 수정을 시작하지 않았는가
- normal 이상 작업에서 큰 단위와 작은 단위를 나누고 작은 단위 기준으로 구현했는가
- 별도 컨펌 없이 진행하기로 한 경우, 큰 단위 안의 작은 단위를 끝까지 닫거나 중단 사유를 명확히 남겼는가
- 요청한 기능이 실제 사용자 흐름에서 끝까지 수행되는가
- 사용자가 현재 화면의 목적, 다음 행동, 완료 행동을 이해할 수 있는가
- 저장, 삭제, 다음 이동, 취소 같은 종료 액션이 작업 흐름의 끝 지점에 있는가
- 빈 상태, 오류 상태, 리로드 상태, 데이터 전환 상태가 깨지지 않는가
- 큰 데이터, 긴 텍스트, 큰 이미지, 작은 이미지에서 레이아웃이 무너지지 않는가
- 기능 추가가 기존 사용자 흐름을 후퇴시키지 않았는가
- 공통으로 처리할 수 있는 UI나 상태 처리를 화면별 임시 구현으로 늘리지 않았는가

## UI 작업 완료 기준

- 주요 화면 폭에서 텍스트, 버튼, 입력, 상태 메시지가 겹치거나 잘리지 않는가
- 동적 크기 변화가 부모 영역 높이를 불필요하게 접었다 펼치지 않는가
- 확대, 축소, 재생, 선택 변경처럼 반복 조작하는 기능이 깜빡임이나 layout shift를 만들지 않는가
- 스크롤이 긴 화면에서 완료 액션을 다시 찾기 위해 사용자가 흐름을 역행하지 않아도 되는가
- 설명 문구가 버튼이나 액션 영역에 밀려 의미를 잃지 않는가
- 버튼 크기와 정렬이 주변 입력, select, 링크와 일관되는가

## 데이터 작업 완료 기준

- 새 데이터 생성, 저장, 삭제 후 목록과 미리보기가 같은 상태를 가리키는가
- 다른 대상이나 다른 데이터로 전환했을 때 이전 상태가 화면에 남지 않는가
- 저장 후 리로드해도 의도한 상태가 복원되는가
- 삭제 후 선택값, 미리보기, 상태 메시지가 안전한 기본 상태로 돌아가는가

## 완료 판정

다음 중 하나라도 확인하지 못했다면 완료 보고에 남은 리스크로 적는다.

- 관련 검증 명령
- 관련 화면 접근
- 콘솔 오류 여부
- 핵심 사용자 시나리오
- 리로드 또는 데이터 전환 시나리오

컨펌 없는 순차 진행에서는 각 단계 종료 시점에도 같은 원칙을 적용한다.

단계가 전체 작업의 일부라면 "완료"는 해당 단계 범위 안에서만 말하고, 전체 완료로 확대하지 않는다.

장기 기능 작업에서는 단계 종료 보고에 다음을 함께 남긴다.

- 이번 단계에서 실제로 닫힌 범위
- 아직 열려 있는 사용자 시나리오
- 검증하지 못한 화면 또는 데이터 흐름
- 다음 단계에서 먼저 확인해야 할 위험

## 검증 분리

완료 보고에서 다음 검증을 서로 대체해서는 안 된다.

- 타입체크/빌드 검증: 코드가 컴파일 가능한지 확인한다.
- API/정적 리소스 검증: 페이지와 번들이 응답하는지 확인한다.
- DOM/상태 검증: 의도한 dataset, scrollTop, 선택값, 저장 상태가 유지되는지 확인한다.
- UX 재현 검증: 실제 사용자 조작 시나리오가 화면에서 안정적으로 보이는지 확인한다.

`check` 또는 `build`가 통과해도 UI 안정성, hover/focus, scroll, layout shift, 깜빡임은 통과한 것으로 간주하지 않는다.

UI 작업 완료 보고에는 다음 중 하나를 반드시 적는다.

- 실제 UX 재현 검증을 수행했고 통과한 시나리오
- 실제 UX 재현 검증을 수행하지 못한 이유와 남은 리스크

## 완료 표현 제한

검증하지 않은 항목은 "완료" 또는 "해결"이라고 표현하지 않는다.

허용 표현:

- "타입/빌드는 통과했다."
- "의도한 방향으로 코드는 수정했다."
- "브라우저 재현 검증은 아직 못 했다."
- "UX 해결 여부는 실제 조작 확인이 필요하다."

금지 표현:

- "검증 완료"라고 말하면서 타입/빌드만 실행한 경우
- "해결됐다"고 말하면서 핵심 사용자 시나리오를 확인하지 않은 경우
- "적용됐다"고 말하면서 실제 DOM 상태나 화면 반영을 확인하지 않은 경우
- "기능 완료"라고 말하면서 일부 단계만 끝낸 경우

## 최종 완료 보고

작업이 실제로 끝났을 때는 최종 완료 보고를 남긴다.

최종 완료 보고에는 다음을 포함한다.

- 전체 목표 상태: 전체 완료인지, 일부 단계 완료인지, 중단인지 명확히 표시한다.
- 전체 단계 진행률: 큰 단계 목록이 있다면 완료/진행 중/남음을 구분한다.
- 최종 완료한 범위
- 아직 남은 범위
- 다음 우선순위
- 변경한 주요 파일
- 실행한 검증
- 실제 화면 검증 여부
- 남은 리스크
- 이어서 하면 좋은 다음 작업

최종 완료 보고는 단계 보고와 구분한다.

긴 작업에서 일부 단계만 끝났다면 최종 완료 보고라고 표현하지 않고, 단계 종료 보고로 남긴다.

## 부분 완료 보고

전체 작업이 남아 있는 상태에서 응답을 종료할 때는 반드시 부분 완료 보고로 남긴다.

부분 완료 보고에는 다음을 포함한다.

- 이번 응답에서 완료한 단계
- 전체 큰 단계 중 현재 위치
- 아직 남은 단계 목록
- 다음에 바로 이어갈 단계
- 실행한 검증과 그 검증이 증명하지 못한 것
- 미검증 항목, 실패한 검증, 도구 문제

남은 단계가 있는데도 "완료", "마무리", "끝"처럼 전체 완료로 오해될 표현을 쓰지 않는다.

사용자가 "논스톱", "컨펌 없이", "쭉 진행"을 요청한 경우에도 최종 응답에는 남은 단계를 생략하지 않는다.

## 최소 보고 템플릿

장기 작업, 단계형 작업, UI/UX 작업, 컨펌 없는 순차 진행 작업에서는 응답을 짧게 쓰더라도 아래 항목을 반드시 포함한다.

- 상태: 전체 완료 / 부분 완료 / 검증 미완료 / 중단 중 하나
- 완료한 범위: 이번 응답에서 실제로 닫힌 단계
- 검증: 실행한 검증과 그 검증이 증명한 것
- 남은 단계: 아직 닫히지 않은 큰 단계 목록. 없을 때만 "남은 단계 없음"이라고 쓴다.
- 다음 우선순위: 다음에 바로 이어갈 첫 작업
- 남은 리스크: 미검증 화면, 데이터, 사용자 시나리오, 도구 문제

남은 단계가 있는데 변경 요약과 검증 결과만 보고하면 보고 실패로 간주한다.

작업이 실제로 전체 완료된 경우에도 "남은 단계 없음"을 명시하고, 대신 후속 개선 후보나 운영 리스크를 분리해서 적는다.

## 누락 방지 체크

응답을 보내기 전 다음 질문에 모두 답할 수 있어야 한다.

- 사용자가 기대한 전체 단계가 무엇이었는가?
- 이번에 닫힌 단계는 무엇인가?
- 아직 닫히지 않은 단계는 무엇인가?
- 다음 단계의 첫 작업은 무엇인가?
- 내가 실행한 검증은 기능, 데이터, UI 중 무엇을 확인했는가?
- 검증하지 못했는데 완료처럼 표현한 항목은 없는가?

하나라도 답하지 못하면 보고를 축약하지 말고 남은 리스크로 적는다.
